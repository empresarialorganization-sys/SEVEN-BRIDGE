REGRAS ATUAIS
- SevenEx é apenas a porta fina de ChatGPT/Codex; inteligência e identidade não ficam no MCP.
- O caminho canônico é OAuth SevenEx -> Bridge valida JWT/audience -> HMAC interno -> Core resolve workspace/browser -> session_id/device_code -> DeviceHub -> WebSocket -> Operator.
- Token OAuth de usuário nunca é repassado ao Core nem a outro serviço.
- Nunca selecionar dispositivo por último visto quando houver mais de um browser vinculado.
- device_code identifica execução, não identidade de usuário, e nunca entra no schema das tools do SevenEx.
- SevenEx/Bridge/Operator usam release 1.1.0; protocolo e capacidades incompatíveis bloqueiam comando com atualização requerida.
- SEVEN_OPERATOR_SHARED_SECRET é segredo permanente serviço-a-serviço; nunca colocar valor no Git, logs, docs ou resposta.
- O hook sevenex_access_token_hook já existe no banco, mas só atua quando habilitado administrativamente no Auth junto do OAuth Server.
- O app/extensão instalados anteriores permanecem funcionais durante a migração até o SevenEx/Operator 1.1.0 passarem E2E.
- O pacote de submissão é metadata do mesmo SevenEx; não cria outro plugin, Bridge, MCP ou extensão.
- Decisão explícita vigente de Daniel em 2026-08-17: o bootstrap Bridge/Cloudflare é temporário para concluir configuração; quando SevenEx + Operator novos passarem E2E real, desativar e remover essa ponte.
- A ponte temporária não substitui o SevenEx canônico e não deve ser expandida silenciosamente para infraestrutura paralela.
- Não criar rota, token, workflow ou endpoint temporário de diagnóstico fora da ponte explicitamente autorizada.
- Não expor segredo de serviço, segredo do device ou URL privada de capacidade em Git, logs, docs ou resposta.
- Preservar política de ilhas: background-first, reutilização de abas gerenciadas, foco protegido e fechamento apenas das abas criadas pela SEVEN.
- Outras compatibilidades antigas só saem após substituição funcional, E2E, busca de consumidores e rollback conhecido.
